2. NestJS architecture

In Express we usually use: routes → controllers → services → models → MongoDB. NestJS implements the same idea in a more structured form.

Request flow

  1. Client / PostmanSends the HTTP request
  2. MiddlewareRequest logging, preliminary processing
  3. Guards → Interceptors → PipesAuthentication, authorization, validation and transformation
  4. ControllerHandles the HTTP request
  5. ServiceRuns the business logic
  6. Mongoose ModelMongoDB queries and document operations
  7. MongoDBUsers, Tickets, Audit Logs
  8. Interceptor → ResponseResponse formatting and logging
This is a simplified diagram. In the real request lifecycle, guards, interceptors and pipes run in a different order and in inbound and outbound phases. We will study that during implementation.

5.7 main.ts: the entry point

import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  await app.listen(process.env.PORT ?? 3000);
}

bootstrap();
  1. import brings functionality from another file or package. Here it brings NestFactory from NestJS.
  2. async function creates an asynchronous function. An asynchronous operation needs waiting until it completes, such as a database connection.
  3. NestFactory.create(AppModule): NestFactory is the mechanism that creates the app, create() creates the application instance, AppModule is the root module, await waits for the operation, and const app stores the instance.
  4. app.listen() starts the server on the given port (3000).
  5. bootstrap() calls the function. Without this call, its code will not run.
main.ts is called the bootstrap file. Bootstrap means initializing and starting the application.

Phase 2 · Lesson 2

2. Module

A module groups related code in one place. In our project: AuthModule (login/register), UsersModule (user management), TicketsModule (ticket management), DashboardModule (analytics). Every feature has its own module.

tickets.module.ts

import { Module } from '@nestjs/common';
import { TicketsController } from './tickets.controller';
import { TicketsService } from './tickets.service';

@Module({
  controllers: [TicketsController],
  providers: [TicketsService],
})
export class TicketsModule {}
  1. import { Module } brings the Module decorator from NestJS.
  2. The next two imports bring our own controller and service.
  3. @Module() tells NestJS which controllers and services belong to this module. controllers are classes that handle requests. providers are services and other injectable components.
  4. export class TicketsModule {} exports the class so other files can import it.

Four properties of @Module()

PropertyMeaning
importsUse other modules
controllersRegister controllers
providersRegister services
exportsMake providers available to other modules
@Module({
  imports: [],
  controllers: [TicketsController],
  providers: [TicketsService],
  exports: [TicketsService],
})
export class TicketsModule {}

exports is useful when another module needs TicketsService.

A module is not an API endpoint. It only organizes the application.
Phase 2 · Lesson 3

3. Controller

A controller receives the client’s request and returns the response. When an employee calls GET /api/v1/tickets, NestJS goes into TicketsController.

tickets.controller.ts

Open src/modules/tickets/tickets.controller.ts and replace the code with:

import { Controller, Get } from '@nestjs/common';
import { TicketsService } from './tickets.service';

@Controller('tickets')
export class TicketsController {

  constructor(
    private readonly ticketsService: TicketsService,
  ) {}

  @Get()
  findAll() {
    return this.ticketsService.findAll();
  }

}
  1. @Controller('tickets'): all endpoints of this controller start with /tickets. Example: /tickets, /tickets/123, /tickets/search.
  2. Constructor: a special method that runs when the class object is created. Here we receive TicketsService through it. This is a very important NestJS concept.
  3. private: the property cannot be accessed directly outside the class.
  4. readonly: after it is initialized in the constructor, it cannot be reassigned.
  5. @Get(): defines the GET HTTP method. On GET /api/v1/tickets, the findAll() method runs.
  6. this: refers to the current class object. this.ticketsService accesses the injected service.

Phase 2 · Lesson 5

5. Dependency Injection (DI)

The most important concept in NestJS. In plain JavaScript you might create the service object yourself:

class TicketsService {
  findAll() {
    return [];
  }
}

class TicketsController {
  ticketsService = new TicketsService();
}

In NestJS we do not do this. We write:

constructor(
  private readonly ticketsService: TicketsService,
) {}

NestJS provides the TicketsService instance itself. This is Dependency Injection.

  1. TicketsControllerNeeds TicketsService
  2. NestJS DI ContainerResolves the dependency
  3. TicketsService instanceThe controller receives it automatically

Benefits of DI

  1. Code becomes reusable.
  2. Testing becomes easy.
  3. Classes stay loosely coupled.
  4. Dependencies are easy to replace.

Singleton

By default, providers in NestJS have singleton scope. Generally one shared instance of a service is kept for the application. A new service object is not created for every request.

8. Connect MongoDB in AppModule

Update src/app.module.ts:

import { Module } from '@nestjs/common';

import { ConfigModule, ConfigService } from '@nestjs/config';

import { MongooseModule } from '@nestjs/mongoose';

import * as Joi from 'joi';

import { TicketsModule } from './modules/tickets/tickets.module';

import configuration from './config/configuration';
import { validationSchema } from './config/validation';

@Module({

  imports: [

    // Environment configuration
    ConfigModule.forRoot({

      isGlobal: true,

      load: [configuration],

      validationSchema,

    }),

    // MongoDB connection
    MongooseModule.forRootAsync({

      imports: [ConfigModule],

      inject: [ConfigService],

      useFactory: (configService: ConfigService) => ({

        uri: configService.getOrThrow<string>('MONGODB_URI'),

      }),

    }),

    // Feature modules
    TicketsModule,

  ],

})

export class AppModule {}

1. ConfigModule.forRoot()

Loads the environment configuration.

  • isGlobal: true: no need to import ConfigModule separately in every feature module.
  • load: [configuration]: registers our configuration file.
  • validationSchema: validates the environment variables.

2. MongooseModule.forRootAsync()

Establishes the MongoDB connection.

  • imports: makes the configuration module available.
  • inject: takes ConfigService as a dependency.
  • useFactory: a function that returns the database connection options.

import { HydratedDocument } from 'mongoose';
import { UserRole } from '../../../common/enums/user-role.enum';

// TypeScript type for a MongoDB User document
export type UserDocument = HydratedDocument<User>;

@Schema({
  timestamps: true,
})
export class User {
  @Prop({
    required: true,
    trim: true,
  })
  name: string;

  @Prop({
    required: true,
    unique: true,
    lowercase: true,
    trim: true,
  })
  email: string;

  @Prop({
    required: true,
    select: false,
  })
  password: string;

  @Prop({
    type: String,
    enum: Object.values(UserRole),
    default: UserRole.EMPLOYEE,
  })
  role: UserRole;

  @Prop({
    default: true,
  })
  isActive: boolean;
}

Line by line

  1. Imports. Schema turns the class into a Mongoose Schema. Prop defines a field inside the class. SchemaFactory generates the actual Mongoose schema from the class.
  2. HydratedDocument<User> is the TypeScript type of a Mongoose document. TypeScript knows the User document has normal fields plus Mongoose document functionality.
  3. @Schema({ timestamps: true }) tells Mongoose to create a schema from this class. timestamps: true adds createdAt and updatedAt automatically.
  4. @Prop() defines the rules of a property (table below).
  5. SchemaFactory.createForClass(User) converts our TypeScript class into a Mongoose schema.
OptionMeaning
requiredField is mandatory
uniqueCreates a unique index
trimRemoves starting and ending spaces
lowercaseConverts the string to lowercase
defaultSets a default value
enumRestricts allowed values
select: falseHides the field in normal queries
unique: true creates a database index. It is not a normal validation rule. Inserting a duplicate email can give a MongoDB duplicate-key error. We will handle it properly later.

select: false on password means the password is not returned in normal queries. Password hashing is added in the Users Service below, and authentication comes in a later lesson. Never save a plain-text password in production.

File: src/modules/users/users.service.ts

import { Injectable, NotFoundException } from '@nestjs/common';
import { InjectModel } from '@nestjs/mongoose';
import { Model } from 'mongoose';

import { User, UserDocument } from './schemas/user.schema';

@Injectable()
export class UsersService {
  constructor(
    @InjectModel(User.name)
    private readonly userModel: Model<UserDocument>,
  ) {}

  // Create user
  async create(data: Partial<User>) {
    const user = await this.userModel.create(data);

    // Do not return password in API response
    return {
      id: user.id,
      name: user.name,
      email: user.email,
      role: user.role,
      isActive: user.isActive,
    };
  }

  // Get all users
  async findAll() {
    return this.userModel.find().exec();
  }

  // Get one user
  async findOne(id: string) {
    const user = await this.userModel.findById(id).exec();

    if (!user) {
      throw new NotFoundException('User not found');
    }

    return user;
  }

  // Update user
  async update(id: string, data: Partial<User>) {
    const user = await this.userModel
      .findByIdAndUpdate(id, data, {
        new: true,
        runValidators: true,
      })
      .exec();

    if (!user) {
      throw new NotFoundException('User not found');
    }

    return user;
  }

  // Delete user
  async remove(id: string) {
    const user = await this.userModel.findByIdAndDelete(id).exec();

    if (!user) {
      throw new NotFoundException('User not found');
    }

    return {
      message: 'User deleted successfully',
    };
  }
}

Explanation

  1. @Injectable() tells NestJS this class can be provided through dependency injection.
  2. @InjectModel(User.name) asks NestJS to provide the registered User Model in our constructor. Now userModel performs MongoDB operations.
  3. Model<UserDocument> tells TypeScript the Model works with User documents.
  4. async and await: a MongoDB operation takes time to complete, so we use asynchronous code. async makes the function asynchronous, await waits for the operation, and .exec() executes the Mongoose query and returns a Promise.
  5. NotFoundException: if the requested User is not in the database, NestJS gives an HTTP 404 Not Found response.
  6. findByIdAndUpdate(id, data, { new: true, runValidators: true }): id is the document to update, data is the changes, new: true returns the updated document, and runValidators: true runs schema validation during the update.
  7. findByIdAndDelete() deletes the document with the given ID.
Security note: this is basic CRUD teaching code. User create/update endpoints do not yet have complete validation, role authorization and (in the first version) password hashing. Do not treat them as production-ready. We add these in the next phases.

import {
  IsEnum,
  IsMongoId,
  IsNotEmpty,
  IsOptional,
  IsString,
  MaxLength,
  MinLength,
} from 'class-validator';

import { TicketCategory } from '../../../common/enums/ticket-category.enum';
import { TicketPriority } from '../../../common/enums/ticket-priority.enum';

export class CreateTicketDto {
  @IsString()
  @IsNotEmpty()
  @MinLength(5)
  @MaxLength(100)

  @IsNotEmpty()
  @MinLength(10)
  @MaxLength(2000)
  description: string;

  @IsEnum(TicketCategory)
  category: TicketCategory;

  @IsOptional()
  @IsEnum(TicketPriority)
  priority?: TicketPriority;

  @IsMongoId()
  createdBy: string;
}

New decorators

1. @IsEnum()

@IsEnum(TicketCategory)
category: TicketCategory;

Only these values are allowed: hardware, software, network, access. If the client sends { "category": "food" }, validation fails.

2. @IsOptional()

@IsOptional()
@IsEnum(TicketPriority)
priority?: TicketPriority;

Priority is optional. If the client does not send it, DTO validation skips this field. The database schema has the default medium, so the default value is applied when saving.

3. @IsMongoId()

@IsMongoId()
createdBy: string;

Checks that the value is in a valid MongoDB ObjectId format.

@IsMongoId() checks only the ID format. It does not confirm that a user with this ID exists in the database. For that, the service needs a database lookup.

5. class-transformer

class-transformer helps transform incoming plain JSON into a DTO class instance and convert values. HTTP query parameters usually arrive as strings:

GET /api/v1/tickets?limit=10&page=2

limit and page arrive from the URL as strings, but we need numbers. For this we use @Type(() => Number).

Example: Pagination DTO

File: src/modules/tickets/dto/ticket-query.dto.ts

import { Type } from 'class-transformer';
import {
  IsInt,
  IsOptional,
  Max,
  Min,
} from 'class-validator';

export class TicketQueryDto {
  @IsOptional()
  @Type(() => Number)
  @IsInt()
  @Min(1)
  page?: number = 1;

  @IsOptional()
  @Type(() => Number)
  @IsInt()
  @Min(1)
  @Max(100)
  limit?: number = 10;
}
  • @Type(() => Number) tells it to convert the string value to a Number.
  • @IsInt(), @Min(1), @Max(100): must be an integer, minimum 1, maximum 100.

@Transform() example

Sometimes we need to modify the input manually.

import { Transform } from 'class-transformer';
import { IsString, IsNotEmpty } from 'class-validator';

export class ExampleDto {
  @Transform(({ value }) =>
    typeof value === 'string' ? value.trim() : value,
  )
  @IsString()
  @IsNotEmpty()
  search: string;
}

If the client sends { "search": " laptop issue " }, the value after transformation is { "search": "laptop issue" }.

@Transform() is for custom transformation. @Type() is commonly used for basic type conversion.

6. Global ValidationPipe

The DTOs have validation decorators, but NestJS must be told to run validation when a request arrives. We use ValidationPipe. File: src/main.ts. Update your existing code:

import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';

import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.setGlobalPrefix('api/v1');

  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,
      forbidNonWhitelisted: true,
      transform: true,
    }),
  );

  await app.listen(process.env.PORT ?? 3000);

  console.log('Server is running on port 3000');
}

bootstrap();

Three important options

1. whitelist: true accepts only the properties defined in the DTO that have validation decorators. Example: the DTO has name, email and password, and the client sends:

{
  "name": "Rahul",
  "email": "rahul@example.com",
  "password": "Rahul@123",
  "isAdmin": true
}

whitelist: true removes the extra isAdmin property.

2. forbidNonWhitelisted: true rejects the request instead of silently removing the extra property. With the same body above, the response is a validation error, because isAdmin is not defined in the DTO.

3. transform: true transforms incoming plain JSON into a DTO class instance. It can also do type conversion through decorators like @Type().

Request validation flow

  1. Client / PostmanSends the request body
  2. Global ValidationPipeChecks the DTO rules
  3. ValidController → Service → Database
  4. Invalid400 Bad Request
Industry tip: with a global pipe you do not call validation manually in every controller. These rules can apply to all incoming requests whose parameters/body are bound to a DTO.

JWT, Passport and bcrypt

  • bcrypt (password security): converts the password into a one-way hash. The original password must not be saved in the database.
  • JWT (login token): after a successful login the server gives a signed token. The client sends this token with protected requests.
  • Passport (authentication framework): provides authentication strategies. We verify the token with the Passport JWT Strategy.

Simple example:

  1. Rahul registers.
  2. His password is hashed with bcrypt and saved in the database.
  3. Rahul logs in.
  4. The server verifies the password.
  5. The server generates a JWT token.
  6. Rahul calls a protected API with the token.
  7. The Passport JWT Strategy verifies the token.
  8. If the token is valid, the request reaches the controller.

How JWT works

  1. Client: LoginEmail + Password
  2. NestJS AuthServiceFind user + bcrypt password compare
  3. JWT ServiceGenerates a signed access token
  4. ClientStores the token and sends it with requests
  5. Passport JWT StrategyVerifies signature and expiration
  6. Protected ControllerAccess is given if the token is valid

A JWT token generally has three parts:

HEADER.PAYLOAD.SIGNATURE
  • Header: algorithm and type of the token.
  • Payload: claims like user ID, email, role.
  • Signature: the token is signed with the server secret.
A JWT is signed, not encrypted. Do not put a password, secret or sensitive personal information in the JWT payload.

5. AuthService: registration and login logic

AuthService has two main methods:

  • register() creates a new user.
  • login() verifies credentials and gives a JWT token.

File: src/modules/auth/auth.service.ts

import {
  Injectable,
  ConflictException,
  UnauthorizedException,
} from '@nestjs/common';

import { JwtService } from '@nestjs/jwt';
import * as bcrypt from 'bcrypt';

import { UsersService } from '../users/users.service';
import { RegisterDto } from './dto/register.dto';
import { LoginDto } from './dto/login.dto';

@Injectable()
export class AuthService {
  constructor(
    private readonly usersService: UsersService,
    private readonly jwtService: JwtService,
  ) {}

  // REGISTER
  async register(data: RegisterDto) {
    const existingUser =
      await this.usersService.findByEmailForAuth(data.email);

    if (existingUser) {
      throw new ConflictException('Email already registered');
    }

    try {
      const user = await this.usersService.create(data);

      return {
        message: 'User registered successfully',
        user,
      };
    } catch (error) {
      // Also handle duplicate email if two requests arrive together
      if (
        typeof error === 'object' &&
        error !== null &&
        'code' in error &&
        error.code === 11000
      ) {
        throw new ConflictException('Email already registered');
      }

      throw error;
    }
  }

  // LOGIN
  async login(data: LoginDto) {
    const user = await this.usersService.findByEmailForAuth(
      data.email,
    );

    if (!user) {
      throw new UnauthorizedException('Invalid email or password');
    }

    if (!user.isActive) {
      throw new UnauthorizedException('Account is inactive');
    }

    const isPasswordValid = await bcrypt.compare(
      data.password,
      user.password,
    );

    if (!isPasswordValid) {
      throw new UnauthorizedException('Invalid email or password');
    }

    // JWT payload
    const payload = {
      sub: user.id,
      email: user.email,
      role: user.role,
    };

    // Generate access token
    const accessToken = await this.jwtService.signAsync(payload);

    return {
      message: 'Login successful',
      accessToken,
      tokenType: 'Bearer',
      user: {
        id: user.id,
        name: user.name,
        email: user.email,
        role: user.role,
      },
    };
  }
}

Important methods

  1. ConflictException: throw new ConflictException('Email already registered'). If the email already exists in the database, the response is HTTP 409 Conflict.
  2. UnauthorizedException: throw new UnauthorizedException('Invalid email or password'). If the email or password is wrong, the response is HTTP 401 Unauthorized. We keep the same error message for email and password so an attacker cannot know whether an email is registered.
  3. bcrypt.compare() returns true or false. data.password is the password sent at login and user.password is the stored hash. We do not decrypt the hash. bcrypt verifies the entered password against the stored hash.
  4. JWT payload: sub means Subject. In a JWT it commonly represents the user’s identity.
  5. signAsync(): the JWT service signs the payload with the secret key and generates the token. Token expiry and secret are configured in AuthModule.

7. JWT Strategy: verify the token

The token was generated at login. When the user calls a protected API later, the server must check whether the token is valid. The Passport JWT Strategy does this.

File: src/modules/auth/strategies/jwt.strategy.ts

import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';

import { PassportStrategy } from '@nestjs/passport';
import { ExtractJwt, Strategy } from 'passport-jwt';

import { UserRole } from '../../../common/enums/user-role.enum';

interface JwtPayload {
  sub: string;
  email: string;
  role: UserRole;
}

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor(
    configService: ConfigService,
  ) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),

      ignoreExpiration: false,

      secretOrKey: configService.getOrThrow<string>('JWT_SECRET'),
    });
  }

  async validate(payload: JwtPayload) {
    return {
      userId: payload.sub,
      email: payload.email,
      role: payload.role,
    };
  }
}

Line by line

  1. PassportStrategy(Strategy): we extend Passport’s JWT Strategy.
  2. ExtractJwt.fromAuthHeaderAsBearerToken(): the token is read from the Authorization header of the HTTP request. 
    Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
    Bearer is the authentication scheme. The actual JWT token comes after it.
  3. ignoreExpiration: false: reject the token if it has expired.
  4. secretOrKey: the token is verified with the same secret that was used when generating it.
  5. validate(): once the token signature and expiry are verified, Passport calls validate(). The returned object is available in the request as req.user. 
    req.user = {
  userId: '671234567890abcdef123456',
  email: 'rahul@example.com',
  role: 'employee',
};
    validate() receives the payload, not the raw token.
Security note: this basic strategy verifies JWT signature and expiry. If a user is deactivated after a token was issued, the existing token can stay valid until it expires. For immediate revocation, we will add options like token version, denylist or a server-side session strategy later.

Logout and refresh token concept

So far we made only an Access Token.

Access Token

  • Short lifetime. Example: 15 minutes.
  • Used to access protected APIs.
  • Sent as a Bearer token in every request.

Refresh Token

  • Used to get a new access token after the access token expires.
  • Usually has a longer lifetime than the access token.
  • Needs secure storage and rotation.

Logout

A JWT access token is stateless. Just deleting the token from the client does not automatically invalidate it on the server. In a real application, mechanisms like refresh-token rotation, token version or a denylist can be implemented for immediate logout/revocation.

What is a Guard?

A Guard is a NestJS feature that decides whether an incoming request can reach the controller.

@UseGuards(AuthGuard('jwt'))

@Roles(UserRole.ADMIN, UserRole.TECHNICIAN)

The second means multiple roles can access the route.

The @Roles() decorator tells the route which roles are allowed. It does not check permission itself. The permission check happens in RolesGuard.

CurrentUser decorator

In Phase 5, JwtStrategy.validate() returned this object, and Passport stores it in request.user:

{
  userId: payload.sub,
  email: payload.email,
  role: payload.role
}

Instead of writing @Req() again and again in the controller, we make a custom decorator. File: src/common/decorators/current-user.decorator.ts

import {
  createParamDecorator,
  ExecutionContext,
} from '@nestjs/common';

import { UserRole } from '../enums/user-role.enum';

export interface AuthenticatedUser {
  userId: string;
  email: string;
  role: UserRole;
}

export const CurrentUser = createParamDecorator(
  (data: unknown, context: ExecutionContext) => {
    const request = context
      .switchToHttp()
      .getRequest<{ user: AuthenticatedUser }>();

    return request.user;
  },
);

createParamDecorator() makes our own custom parameter decorator. Now we can use it in the controller:

@Get('profile')
getProfile(@CurrentUser() user: AuthenticatedUser) {
  return user;
}

Result:

{
  "userId": "671234567890abcdef123456",
  "email": "rahul@example.com",
  "role": "employee"
}

Benefit: the controller gets the logged-in user directly. The client does not need to send their own user ID in the request body.

RolesGuard: the most important part

File: src/common/guards/roles.guard.ts

import {
  Injectable,
  CanActivate,
  ExecutionContext,
} from '@nestjs/common';

import { Reflector } from '@nestjs/core';

import { ROLES_KEY } from '../decorators/roles.decorator';
import { AuthenticatedUser } from '../decorators/current-user.decorator';
import { UserRole } from '../enums/user-role.enum';

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(
    private readonly reflector: Reflector,
  ) {}

  canActivate(context: ExecutionContext): boolean {
    // Read allowed roles from @Roles()
    const requiredRoles = this.reflector.getAllAndOverride<UserRole[]>(
      ROLES_KEY,
      [
        context.getHandler(),
        context.getClass(),
      ],
    );

    // No role restriction means any authenticated user can continue
    if (!requiredRoles || requiredRoles.length === 0) {
      return true;
    }

    // Get logged-in user from request
    const request = context
      .switchToHttp()
      .getRequest<{ user?: AuthenticatedUser }>();

    const user = request.user;

    // Check user's role
    return !!user && requiredRoles.includes(user.role);
  }
}

In simple language

  1. CanActivate: export class RolesGuard implements CanActivate. It is a NestJS interface. A guard must implement the canActivate() method, which decides: true means the request can go ahead, false means it is rejected.
  2. Reflector is used to read metadata. Remember we set metadata with @Roles(UserRole.ADMIN). The Reflector reads that metadata.
  3. getAllAndOverride() checks the metadata of both the handler and the controller class. context.getHandler() is the current route’s metadata, context.getClass() is the controller’s metadata, and ROLES_KEY is the metadata key.
  4. User information: const user = request.user; This comes from Phase 5’s JwtStrategy.validate().
  5. Role matching: return !!user && requiredRoles.includes(user.role); If requiredRoles = ['admin'] and user.role = 'employee', the result is false. If user.role = 'admin', the result is true.

Now our custom RolesGuard is ready.

8. TicketsService: role and ownership checks

This is the most important practical part of the lesson. We implement:

  • An employee sees only their own tickets.
  • A technician sees only assigned tickets.
  • An admin sees all tickets.
  • An employee edits only their own open ticket.
  • A technician updates the status only of an assigned ticket.
  • An admin can assign, update or delete any ticket.

File: src/modules/tickets/tickets.service.ts. Update your existing service with this implementation:

import {
  Injectable,
  NotFoundException,
  ForbiddenException,
} from '@nestjs/common';

import { InjectModel } from '@nestjs/mongoose';
import { Model, Types } from 'mongoose';

import { Ticket, TicketDocument } from './schemas/ticket.schema';

import { UsersService } from '../users/users.service';

import { CreateTicketDto } from './dto/create-ticket.dto';
import { UpdateTicketDto } from './dto/update-ticket.dto';

import { UserRole } from '../../common/enums/user-role.enum';
import { TicketStatus } from '../../common/enums/ticket-status.enum';

import { AuthenticatedUser } from '../../common/decorators/current-user.decorator';

@Injectable()
export class TicketsService {
  constructor(
    @InjectModel(Ticket.name)
    private readonly ticketModel: Model<TicketDocument>,

    private readonly usersService: UsersService,
  ) {}

  // 1. Create ticket
  async create(data: CreateTicketDto, user: AuthenticatedUser) {
    const ticket = await this.ticketModel.create({
      ...data,
      createdBy: new Types.ObjectId(user.userId),
    });

    return ticket;
  }

  // 2. Get tickets according to logged-in user's role
  async findAllForUser(user: AuthenticatedUser) {
    let filter = {};

    if (user.role === UserRole.EMPLOYEE) {
      filter = {
        createdBy: new Types.ObjectId(user.userId),
      };
    } else if (user.role === UserRole.TECHNICIAN) {
      filter = {
        assignedTo: new Types.ObjectId(user.userId),
      };
    }

    return this.ticketModel
      .find(filter)
      .populate('createdBy', 'name email role')
      .populate('assignedTo', 'name email role')
      .sort({ createdAt: -1 })
      .exec();
  }

  // 3. Get one ticket after checking access
  async findOneForUser(id: string, user: AuthenticatedUser) {
    const ticket = await this.ticketModel.findById(id).exec();

    if (!ticket) {
      throw new NotFoundException('Ticket not found');
    }

    const isAdmin = user.role === UserRole.ADMIN;

    const isOwner =
      ticket.createdBy.toString() === user.userId;

    const isAssignedTechnician =
      ticket.assignedTo?.toString() === user.userId;

    if (!isAdmin && !isOwner && !isAssignedTechnician) {
      throw new ForbiddenException(
        'You do not have permission to view this ticket',
      );
    }

    await ticket.populate('createdBy', 'name email role');
    await ticket.populate('assignedTo', 'name email role');

    return ticket;
  }

  // 4. Employee can edit own open ticket; Admin can edit any ticket
  async updateOwnTicket(
    id: string,
    data: UpdateTicketDto,
    user: AuthenticatedUser,
  ) {
    const ticket = await this.ticketModel.findById(id).exec();

    if (!ticket) {
      throw new NotFoundException('Ticket not found');
    }

    const isAdmin = user.role === UserRole.ADMIN;

    const isOwner =
      ticket.createdBy.toString() === user.userId;

    const isOpen = ticket.status === TicketStatus.OPEN;

    if (!isAdmin && !(user.role === UserRole.EMPLOYEE && isOwner && isOpen)) {
      throw new ForbiddenException(
        'You can only edit your own open tickets',
      );
    }

    ticket.set(data);

    await ticket.save();

    return ticket;
  }

  // 5. Update ticket status
  async updateStatus(
    id: string,
    status: TicketStatus,
    user: AuthenticatedUser,
  ) {
    const ticket = await this.ticketModel.findById(id).exec();

    if (!ticket) {
      throw new NotFoundException('Ticket not found');
    }

    const isAdmin = user.role === UserRole.ADMIN;

    const isAssignedTechnician =
      user.role === UserRole.TECHNICIAN &&
      ticket.assignedTo?.toString() === user.userId;

    if (!isAdmin && !isAssignedTechnician) {
      throw new ForbiddenException(
        'Only Admin or assigned Technician can update ticket status',
      );
    }

    ticket.status = status;

    await ticket.save();

    return ticket;
  }

  // 6. Assign technician - Admin only route
  async assignTechnician(id: string, technicianId: string) {
    const ticket = await this.ticketModel.findById(id).exec();

    if (!ticket) {
      throw new NotFoundException('Ticket not found');
    }

    const technician = await this.usersService.findOne(technicianId);

    if (technician.role !== UserRole.TECHNICIAN) {
      throw new ForbiddenException(
        'Selected user is not a technician',
      );
    }

    if (!technician.isActive) {
      throw new ForbiddenException(
        'Technician account is inactive',
      );
    }

    ticket.assignedTo = new Types.ObjectId(technicianId);

    await ticket.save();

    return ticket;
  }

  // 7. Delete ticket - Admin only route
  async remove(id: string) {
    const ticket = await this.ticketModel
      .findByIdAndDelete(id)
      .exec();

    if (!ticket) {
      throw new NotFoundException('Ticket not found');
    }

    return {
      message: 'Ticket deleted successfully',
    };
  }
}

Important concepts in this code

A. findAllForUser()

if (user.role === UserRole.EMPLOYEE) {
  filter = {
    createdBy: new Types.ObjectId(user.userId),
  };
}

An employee gets only their own tickets. For a technician:

filter = {
  assignedTo: new Types.ObjectId(user.userId),
};

For an admin the filter is empty (filter = {};), so the admin can see all tickets.

B. ForbiddenException

throw new ForbiddenException(
  'You do not have permission to view this ticket',
);

The user is logged in but does not have permission to access that ticket. So the response is 403 Forbidden.

C. ticket.set(data)

ticket.set(data);
await ticket.save();

Only the fields permitted by the DTO are set on the document, and then the document is saved.

D. assignedTo

ticket.assignedTo = new Types.ObjectId(technicianId);

The selected technician’s ObjectId is saved in the ticket.

E. Why a permission check in the service too? A Guard on the controller is one security layer. The ownership check in the service is the second layer. For example, an employee can be allowed to access the route /tickets/123, but that does not mean they can access every ticket ID. The service checks the owner of that specific ticket.

Security improvement: reject an unknown role

findAllForUser() used an empty filter for admin. To stop an unknown role from accidentally getting all tickets, keep the method in this safer version:

async findAllForUser(user: AuthenticatedUser) {
  let filter: Record<string, Types.ObjectId> = {};

  if (user.role === UserRole.EMPLOYEE) {
    filter = {
      createdBy: new Types.ObjectId(user.userId),
    };
  } else if (user.role === UserRole.TECHNICIAN) {
    filter = {
      assignedTo: new Types.ObjectId(user.userId),
    };
  } else if (user.role !== UserRole.ADMIN) {
    throw new ForbiddenException('Invalid user role');
  }

  return this.ticketModel
    .find(filter)
    .populate('createdBy', 'name email role')
    .populate('assignedTo', 'name email role')
    .sort({ createdAt: -1 })
    .exec();
}

Now only admin gets the empty filter and can see all tickets.

import {
  Controller,
  Post,
  Get,
  Patch,
  Delete,
  Body,
  Param,
  UseGuards,
} from '@nestjs/common';

import { TicketsService } from './tickets.service';

import { CreateTicketDto } from './dto/create-ticket.dto';
import { UpdateTicketDto } from './dto/update-ticket.dto';
import { UpdateTicketStatusDto } from './dto/update-ticket-status.dto';
import { AssignTicketDto } from './dto/assign-ticket.dto';

import { JwtAuthGuard } from '../../common/guards/jwt-auth.guard';
import { RolesGuard } from '../../common/guards/roles.guard';

import { Roles } from '../../common/decorators/roles.decorator';
import { CurrentUser } from '../../common/decorators/current-user.decorator';
import { AuthenticatedUser } from '../../common/decorators/current-user.decorator';

import { UserRole } from '../../common/enums/user-role.enum';

@Controller('tickets')
@UseGuards(JwtAuthGuard, RolesGuard)
export class TicketsController {
  constructor(
    private readonly ticketsService: TicketsService,
  ) {}

  // Create ticket
  @Post()
  create(
    @Body() body: CreateTicketDto,
    @CurrentUser() user: AuthenticatedUser,
  ) {
    return this.ticketsService.create(body, user);
  }

  // Get tickets visible to logged-in user
  @Get()
  findAll(
    @CurrentUser() user: AuthenticatedUser,
  ) {
    return this.ticketsService.findAllForUser(user);
  }

  // Get one ticket
  @Get(':id')
  findOne(
    @Param('id') id: string,
    @CurrentUser() user: AuthenticatedUser,
  ) {
    return this.ticketsService.findOneForUser(id, user);
  }

  // Edit own open ticket, or Admin can edit
  @Patch(':id')
  update(
    @Param('id') id: string,
    @Body() body: UpdateTicketDto,
    @CurrentUser() user: AuthenticatedUser,
  ) {
    return this.ticketsService.updateOwnTicket(id, body, user);
  }

  // Admin or Technician can update status
  @Roles(UserRole.ADMIN, UserRole.TECHNICIAN)
  @Patch(':id/status')
  updateStatus(
    @Param('id') id: string,
    @Body() body: UpdateTicketStatusDto,
    @CurrentUser() user: AuthenticatedUser,
  ) {
    return this.ticketsService.updateStatus(
      id,
      body.status,
      user,
    );
  }

  // Admin can assign technician
  @Roles(UserRole.ADMIN)
  @Patch(':id/assign')
  assignTechnician(
    @Param('id') id: string,
    @Body() body: AssignTicketDto,
  ) {
    return this.ticketsService.assignTechnician(
      id,
      body.technicianId,
    );
  }

  // Admin can delete ticket
  @Roles(UserRole.ADMIN)
  @Delete(':id')
  remove(
    @Param('id') id: string,
  ) {
    return this.ticketsService.remove(id);
  }
}

3. Custom Global Exception Filter

File: src/common/filters/all-exceptions.filter.ts. Write this code carefully:

import {
  ArgumentsHost,
  Catch,
  ExceptionFilter,
  HttpException,
  HttpStatus,
  Logger,
} from '@nestjs/common';

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger(AllExceptionsFilter.name);

  catch(exception: unknown, host: ArgumentsHost) {
    const context = host.switchToHttp();

    const request = context.getRequest();
    const response = context.getResponse();

    let statusCode = HttpStatus.INTERNAL_SERVER_ERROR;
    let message: string | string[] = 'Internal server error';
    let error = 'Internal Server Error';

    // 1. NestJS HTTP exceptions
    if (exception instanceof HttpException) {
      statusCode = exception.getStatus();

      const exceptionResponse = exception.getResponse();

      if (typeof exceptionResponse === 'string') {
        message = exceptionResponse;
      } else if (
        typeof exceptionResponse === 'object' &&
        exceptionResponse !== null &&
        'message' in exceptionResponse
      ) {
        const responseMessage = exceptionResponse.message;

        if (
          typeof responseMessage === 'string' ||
          Array.isArray(responseMessage)
        ) {
          message = responseMessage as string | string[];
        } else {
          message = exception.message;
        }
      } else {
        message = exception.message;
      }

      error = exception.name;
    }

    // 2. MongoDB duplicate key error
    else if (
      typeof exception === 'object' &&
      exception !== null &&
      'code' in exception &&
      exception.code === 11000
    ) {
      statusCode = HttpStatus.CONFLICT;
      message = 'A record with this value already exists';
      error = 'Conflict';
    }

    // 3. MongoDB invalid ObjectId / CastError
    else if (
      typeof exception === 'object' &&
      exception !== null &&
      'name' in exception &&
      exception.name === 'CastError'
    ) {
      statusCode = HttpStatus.BAD_REQUEST;
      message = 'Invalid ID or value format';
      error = 'Bad Request';
    }

    // 4. Mongoose validation error
    else if (
      typeof exception === 'object' &&
      exception !== null &&
      'name' in exception &&
      exception.name === 'ValidationError'
    ) {
      statusCode = HttpStatus.BAD_REQUEST;
      message = 'Database validation failed';
      error = 'Bad Request';
    }

    // 5. Log server-side error details
    if (statusCode >= 500) {
      this.logger.error(
        exception instanceof Error
          ? exception.stack
          : String(exception),
      );
    }

    // 6. Send consistent error response
    response.status(statusCode).json({
      success: false,
      statusCode,
      error,
      message,
      timestamp: new Date().toISOString(),
      path: request.url,
    });
  }
}

Important parts

  1. @Catch() means the filter can catch all types of exceptions. If we wrote @Catch(HttpException), the filter would handle only HttpException type errors.
  2. ExceptionFilter: export class AllExceptionsFilter implements ExceptionFilter. It is a NestJS interface. It is compulsory to implement the catch() method.
  3. ArgumentsHost: catch(exception: unknown, host: ArgumentsHost). exception is the error that occurred. host is the current execution context.
  4. switchToHttp() says we are working in the HTTP request-response context.
  5. getRequest() and getResponse() give access to the current request and response objects.
  6. exception instanceof HttpException checks whether the error is a NestJS HTTP exception.
  7. MongoDB error code 11000. When a duplicate unique field is inserted, MongoDB can give a duplicate-key error. Example: rahul@example.com already exists and we try to insert it again. We convert it to HTTP 409 Conflict.
  8. statusCode >= 500: we keep the details of server errors in the server-side log. We do not expose the internal stack trace or database details to the client.
In production, never return stack traces, database internals, passwords and secrets in the API response.

5. Interceptor and the Response Interceptor

The Exception Filter handles errors. An Interceptor can execute additional logic around a request or a response.

Common uses

  • Standardize the API response format.
  • Measure request execution time.
  • Logging.
  • Response transformation.
  • Caching.

In our project, we use an interceptor to convert the success response into a standard format.

Exception Filter vs Interceptor

Exception FilterInterceptor
Handles exceptionsLogic around request/response
Formats the error responseCan format the success response
catch() methodintercept() method
Error handlingResponse transformation, logging, caching
  1. Client Request
  2. NestJS Controller + Service
  3. Success: the Interceptor transforms the response. Error: the Exception Filter formats the error.
  4. Consistent API Response

Custom Response Interceptor

File: src/common/interceptors/transform.interceptor.ts

import {
  Injectable,
  NestInterceptor,
  ExecutionContext,
  CallHandler,
} from '@nestjs/common';

import { Observable, map } from 'rxjs';

@Injectable()
export class TransformInterceptor implements NestInterceptor {
  intercept(
    context: ExecutionContext,
    next: CallHandler,
  ): Observable<unknown> {
    const request = context.switchToHttp().getRequest();
    const response = context.switchToHttp().getResponse();

    return next.handle().pipe(
      map((data) => {
        return {
          success: true,
          statusCode: response.statusCode,
          message: 'Request successful',
          data,
          timestamp: new Date().toISOString(),
          path: request.url,
        };
      }),
    );
  }
}
  1. NestInterceptor: export class TransformInterceptor implements NestInterceptor. It is a NestJS interface used to build an interceptor class.
  2. ExecutionContext provides the context of the current request.
  3. CallHandler: next.handle() executes the actual controller handler and returns its response stream.
  4. Observable: NestJS interceptors work with RxJS Observables.
  5. pipe() and map(): map() transforms the data coming from the controller.

Example: the controller returns

{
  "name": "Rahul",
  "email": "rahul@example.com"
}

and the interceptor converts it to:

{
  "success": true,
  "statusCode": 200,
  "message": "Request successful",
  "data": {
    "name": "Rahul",
    "email": "rahul@example.com"
  },
  "timestamp": "2026-10-31T10:00:00.000Z",
  "path": "/api/v1/users/profile"
}

7. try/catch, hiding internal errors and Logger

When should you use try/catch?

Beginners often put try/catch in every service method. It is not needed everywhere.

async findOne(id: string) {
  const ticket = await this.ticketModel.findById(id).exec();

  if (!ticket) {
    throw new NotFoundException('Ticket not found');
  }

  return ticket;
}

No manual try/catch is needed here. If a Mongoose error occurs, it propagates to the global Exception Filter.

When is try/catch useful? When you want to handle or translate a specific error.

async createUser(data: CreateUserDto) {
  try {
    return await this.userModel.create(data);
  } catch (error) {
    // Handle a known database error here if needed
    throw error;
  }
}

Catching and throwing the same error gives no extra benefit. So it is better to write it simply:

async createUser(data: CreateUserDto) {
  return this.userModel.create(data);
}
Rule: catch an error only when you will take a meaningful action on it, recover from it, or convert it into an appropriate application exception.

Production security improvement: hide internal errors

In our Exception Filter, if the HTTP status is 500, the client should get a generic message. Internal exception details must not be exposed. In the filter, after the HttpException processing, add this condition:

if (statusCode >= 500) {
  message = 'Internal server error';
  error = 'Internal Server Error';
}

The server-side Logger still records the actual error stack.

What the client gets:

{
  "success": false,
  "statusCode": 500,
  "error": "Internal Server Error",
  "message": "Internal server error",
  "timestamp": "2026-10-31T10:00:00.000Z",
  "path": "/api/v1/tickets"
}

In the server log: the actual exception details and stack trace. This keeps debugging possible and does not expose internal implementation details to the client.

Logging with the NestJS Logger

In a production application we must log important events along with errors. We can use NestJS’s built-in Logger.

import { Injectable, Logger } from '@nestjs/common';

@Injectable()
export class TicketsService {
  private readonly logger = new Logger(TicketsService.name);

  async example() {
    this.logger.log('Ticket operation started');

    this.logger.warn('Ticket needs attention');

    this.logger.error('Ticket operation failed');
  }
}
MethodUse
log()General information
error()Error information
warn()Warning
debug()Debugging
verbose()Detailed diagnostic logs
this.logger.log('Ticket created successfully');

The output shows the service’s context along with the log.

9. Architecture: Filter vs Interceptor vs Guard vs Pipe

These four concepts are very important in NestJS.

ComponentMain responsibilityExample
MiddlewareInitial logic when a request arrivesRequest logging
GuardPermission checkJWT, RBAC
PipeInput validation/transformationValidationPipe
InterceptorRequest/response transformationSuccess response format
Exception FilterHandle errors400, 401, 500

A simple way to remember:

  • Middleware: the request arrived.
  • Guard: is there permission?
  • Pipe: is the data valid?
  • Controller/Service: the actual business logic.
  • Interceptor: transform the response.
  • Exception Filter: handle the error.
